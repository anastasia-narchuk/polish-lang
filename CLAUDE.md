# CLAUDE.md — как работать в этом проекте

Claude Code читает этот файл сам в начале каждой сессии, если он есть в ветке, с которой сессия стартует. Поэтому его место — в `main`: пока PR #2 не влит, начинать сессию с ветки из `HANDOFF.md`.

Проект — iOS-приложение на SwiftUI для подготовки к госэкзамену по польскому (`ios/`). Что, как и где — в `README.md`. Текущее состояние работы — в `HANDOFF.md`.

## Общение

- Только русский или английский, **никогда украинский**.
- ТЗ и спорные места: если ТЗ противоречит коду или `HANDOFF.md`, сначала спросить, потом делать.

## Начало сессии — до любой работы

1. **Найти и прочитать `HANDOFF.md` целиком.** Если в текущей ветке его нет, искать во всех ветках:
   ```bash
   git fetch --all --prune
   ```
   ```bash
   git log --all --date=short --format='%h %ad %D %s' -- HANDOFF.md | head
   ```
   ```bash
   git show origin/<ветка>:HANDOFF.md
   ```
   Актуальный — с самым свежим коммитом. Без хендоффа не начинать: в сессии 02.11 работа без него ушла не в ту сторону и была откачена.
2. **Прочитать `README.md`.**
3. **Сверить ветки.** Рабочую ветку назначает среда; код может лежать в ветке из хендоффа. Если рабочая ветка пустая или отстаёт, влить ту: `git merge origin/<ветка из HANDOFF>`. Сказать пользователю, в какой ветке идёт работа.
4. **Проверить последний CI и открытые PR** (GitHub MCP: `actions_list` → `list_workflow_runs`, `list_pull_requests`).
5. **Отчитаться пользователю в 3–5 строках:** где остановились, следующий шаг из разд. 8 хендоффа, какие открытые решения из разд. 3 касаются задачи. Дальше — по команде.
6. **Новое ТЗ сверить с кодом до работы.** Платформа — iOS: пункты ТЗ про веб-артефакт «Pisz po polsku», polish-learner, localStorage, Mongo к iOS неприменимы или требуют перевода на iOS. Вопросы по противоречиям задать до кода. ТЗ сохранять в `docs/tz/` (с согласия пользователя), чтобы не зависеть от вложений чата.

## Во время работы

- **Интерфейс** — только через дизайн-систему `ios/PolishLang/UI/Design` (`Theme.swift`, `Components.swift`): пилюли `.buttonStyle(.pill(...))`, `cardBackground()`, `FeatureCard`, `SegmentedPills`, `Font.ui`. Системные `.bordered`, `Form` и сгруппированные списки не использовать.
- **Проверка перед пушем:** `cd ios && swift test` для ядра, `swiftc -parse` для UI (тулчейн — в `HANDOFF.md`, разд. 6). Типы UI проверяет только CI: после пуша дождаться CI и посмотреть скриншоты.
- **Git:**
  - небольшие коммиты, пуш в рабочую ветку;
  - PR не создавать без просьбы;
  - историю не переписывать (force-push блокируется), откатывать через `git revert`.
- **Хендофф по ходу:** решение, которое пользователь не подтвердил, сразу записывать в разд. 3 `HANDOFF.md`, а не держать в контексте.

## Когда писать хендофф

- В конце каждой сессии и перед переходом к новой большой задаче.
- **Когда контекст заполнен на 60–70%** (в Claude Code — команда `/context`). Не ждать автоматического сжатия: оно пересказывает историю и теряет как раз нюансы — дословные формулировки пользователя, причины решений, неудачные попытки.
- Признаки, что пора, даже без `/context`:
  - много скриншотов и больших файлов в разговоре;
  - сделано 2–3 крупные задачи;
  - ответы начинают путать ранние детали.
- После хендоффа продолжать в новой сессии.

## Как писать `HANDOFF.md`

Один файл в корне репозитория. Это **текущее состояние, а не дневник**: каждая сессия переписывает его целиком, дописывается только «Журнал сессий» внизу. Дословные блоки (критерии приёмки, промпты) переносить без изменений, если код не менялся. Архитектуру и стек не описывать — ссылка на README.

Шапка: дата, рабочая ветка, открытые PR, последний зелёный CI (ссылка, коммит).

1. **ТЗ** (ТЗ 1, ТЗ 2, …): статус каждого — сделано / частично / не начато. Критерии приёмки дословно; у каждого «проверено» (чем: юнит-тест с именем, скриншот CI, устройство) или «не проверено» с причиной.
2. **Отклонения от ТЗ и почему.** Итоговый текст каждого промпта дословно, с пометкой, что изменено относительно ТЗ.
3. **ОТКРЫТЫЕ решения**, ждущие подтверждения пользователя, пронумерованные. Подтверждённые помечать датой и цитатой.
4. **Что добавлено сверх ТЗ** и как это запускать.
5. **Что пробовали и не сработало:** что, почему, чем заменили, чего не повторять.
6. **Ключевые файлы и функции по фичам**, команды сборки и тестов (в блоках кода), известные баги и TODO.
7. **Требования и ограничения пользователя** из всех сессий; важные — цитатами.
8. **Следующий шаг:** что делать и чего не начинать без команды.

Внизу — **Журнал сессий**: дата, ветка, что сделано, в 1–3 строки.

**Перед коммитом проверить:**
- каждое требование пользователя из этой сессии есть в разд. 7 или выполнено;
- каждое неподтверждённое решение есть в разд. 3;
- каждое «проверено» подтверждено фактом (тест, скриншот, ссылка на CI);
- пути от корня репозитория, команды копируются и работают.

**Завершение:** закоммитить `HANDOFF.md` (и `CLAUDE.md`, если менялся), запушить в рабочую ветку, в ответе дать название ветки и ссылку `https://github.com/anastasia-narchuk/polish-lang/blob/<ветка>/HANDOFF.md`.

## Конец сессии

- Всё закоммичено и запушено. CI зелёный, или причина красного записана в хендофф.
- Описание открытого PR (если он есть) соответствует содержимому ветки.
- `HANDOFF.md` обновлён по правилам выше.
